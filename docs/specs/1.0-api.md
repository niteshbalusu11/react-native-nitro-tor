# 1.0 API acceptance specification

This document records the design agreed for issue #11 and is the implementation review target for `1.0.0-rc.1`.

## Public API

- Export `Tor` and `TorError`; do not retain pre-1.0 compatibility aliases.
- Group operations under `Tor.daemon`, `Tor.http`, and `Tor.hiddenServices`.
- Keep data-directory ownership with the caller through `dataDirectory`.
- Reject operational failures with stable typed error codes.

## Daemon lifecycle

- Own one process-wide native Tor daemon.
- `start` resolves only after full bootstrap. Identical calls share the attempt; conflicting configurations reject.
- Publish full ordered status snapshots for stopped, starting, running, stopping, and failed states.
- Include structured bootstrap progress and running connectivity.
- Refresh status after foreground resume without permanent polling.
- Make `stop` idempotent. It cancels startup and HTTP work, closes onion services, and waits for daemon exit.
- Allow retry from failed state. `requestNewIdentity` is valid only while running.

## HTTP

- Provide one structured request method and concurrent native requests.
- Resolve all HTTP response status codes, including 4xx and 5xx; reject transport failures.
- Return text bodies and lowercase multi-value response headers.
- Support request timeouts and explicit invalid-certificate opt-in.

## Onion services

- Accept an optional caller-owned 64-byte private key and return the generated or supplied key.
- Do not persist or restore keys automatically.
- Reject duplicate creation and make removal idempotent.
- Keep the authenticated control connection private and close services through its owner.

## Release verification

- Cover parsers, lifecycle state/validation/error mapping, TypeScript facade behavior, and real daemon integration.
- Exercise background/foreground reconciliation in the mobile example.
- Verify the iOS and Android ZEUS app before promoting the release candidate to stable.
